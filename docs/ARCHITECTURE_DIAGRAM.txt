================================================================================
            PEDIDOS API - Fluxo de um POST /api/v1/orders (arquitetura atual)
================================================================================

Camadas (Arquitetura Hexagonal; regra verificada pelo ArchitectureTest):

  infrastructure  ->  application  ->  domain
  (Spring, web,       (casos de uso,     (Order, Money, OrderStatus;
   adaptadores,        portas,            sem nenhum framework)
   observabilidade)    paginação)

--------------------------------------------------------------------------------
 Requisição
--------------------------------------------------------------------------------

 cliente ──HTTP (traceparent opcional)──► Tomcat, uma THREAD VIRTUAL por requisição
                                          span: "http post /api/v1/orders"
   │
   ▼
 OrderController                                  [infrastructure/adapter/in/web]
   │  valida o corpo (Bean Validation) -> 400 RFC 7807 se inválido
   ▼
 CreateOrderUseCaseImpl                           [application/usecase]
   │  dispara as duas chamadas EM PARALELO no executor de threads virtuais
   │  (ContextExecutorService: leva span e MDC para cada thread)
   │
   ├──► thread virtual A: CustomerValidationPort
   │      SimulatedCustomerValidationAdapter      span "customer-validation"
   │      sleep 150 ms (I/O simulado)             timer orders.validation.customer.duration
   │
   └──► thread virtual B: ShippingCalculationPort
          SimulatedShippingCalculationAdapter     span "shipping-calculation"
          sleep 200 ms (I/O simulado)             timer orders.calculation.shipping.duration
   │
   │  espera as duas com timeout (APP_DEPENDENCIES_TIMEOUT, padrão 2s)
   │    - estourou o prazo      -> DependencyUnavailableException -> 503
   │    - erro no adaptador     -> repassado com a causa real
   ▼
 Order.create(...)                                [domain/model]
   │  regras: itens não vazios, mesma moeda (422 se violadas), total = itens + frete
   ▼
 OrderRepositoryPort.save  -> InMemoryOrderRepositoryAdapter (local ao processo)
   │
   ▼
 OrderController registra:
   - métricas: orders.succeeded{currency}, orders.total.value{currency},
               orders.by.status{status=PENDING}, orders.create.duration
   - log ECS "Pedido criado" com order_id, status, duration_ms, thread_type, traceId
   ▼
 201 Created + Location: /api/v1/orders/{id}

 Tempo total esperado: ~200 ms (o maior dos dois atrasos), não 350 ms (a soma),
 porque validação e frete rodam em paralelo.

--------------------------------------------------------------------------------
 Transição de status (PATCH /api/v1/orders/{id}/status)
--------------------------------------------------------------------------------

 PENDING ──► CONFIRMED ──► PROCESSING ──► SHIPPED ──► DELIVERED
    │            │              │             │
    └────────────┴──────────────┴─────────────┴──► CANCELLED

 - Transição fora do diagrama (inclusive voltar a PENDING) -> 422.
 - Order.changeStatusTo é atômica (ReentrantLock, que não prende a thread virtual
   ao carrier como o synchronized no Java 21): requisições concorrentes não
   aplicam duas transições a partir do mesmo status.

--------------------------------------------------------------------------------
 Telemetria
--------------------------------------------------------------------------------

 Métricas  -> /actuator/prometheus e envio nativo ao Pushgateway   (OBSERVABILITY.md)
 Traces    -> OTLP HTTP para o Jaeger                                (TRACING.md)
 Logs      -> stdout em JSON ECS, com traceId/spanId, sem PII nem valores

 Como comparar threads virtuais x de plataforma: rodar a mesma carga com
 spring.threads.virtual.enabled=true e depois false, e comparar
 http_server_requests_seconds (latência), jvm_threads_live_threads e
 jvm_threads_virtual_live_threads{scheduling_status="queued"}.
 Registre os números medidos; não use valores de exemplo como resultado.
